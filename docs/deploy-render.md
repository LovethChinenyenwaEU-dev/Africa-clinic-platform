# Deploying AfriPeak Health on Render

Week 12. Everything runs on Render's free plan from one file, [`render.yaml`](../render.yaml)
(a Render "Blueprint"). Five pieces:

| Render name | What it is | Address |
|---|---|---|
| `afripeak-api` | the FastAPI backend (also runs the reminder worker) | `https://afripeak-api.onrender.com` |
| `afripeak-web` | the clinic app (staff and patients) | `https://afripeak-web.onrender.com` |
| `afripeak-landing` | the public landing page | `https://afripeak-landing.onrender.com` |
| `afripeak-redis` | Key Value (Redis) for the worker's heartbeat | inside Render only |
| `afripeak-db` | PostgreSQL 16 | Render gives an internal and an external address |

No real patient data. This is a demo and pilot set-up with fake people only (see the
README warning).

## What the free plan means

- **Sleeping.** A free web service sleeps after 15 minutes without visitors. The first visit
  after that takes about a minute. If the clinic app shows "The service is unavailable", the
  API was still waking: wait a few seconds and try again. Opening
  `https://afripeak-api.onrender.com/health` first wakes it.
- **Reminders** run inside the API (`RUN_WORKER_IN_API=true`), because free plans have no
  background workers. They only go out while the API is awake, and `SMS_PROVIDER=none`
  sends nothing anyway. For a real pilot, move to a paid plan and add a background worker
  running `python -m app.worker` (then set `RUN_WORKER_IN_API=false`).
- **The free database is deleted 30 days after it is created**, unless upgraded (14 days'
  grace). Note the date you create it.
- 750 free hours a month are shared by all free services in the workspace. Three sleeping
  services stay well inside that; do not set up anything that keeps them awake all the time.

## 1. Before you start

1. All CI jobs green on `main`, including **Production images (build)**.
2. A Render account (sign up with GitHub), with access to the repository.

## 2. Create everything from the Blueprint

1. Render dashboard: **New > Blueprint**, choose the repository, branch `main`.
2. Render reads `render.yaml` and lists the five pieces. Click **Apply**.
3. Wait for the three web services to show **Live** (the first build takes several minutes).

If a name was taken, Render adds a suffix (for example `afripeak-web-x1y2.onrender.com`).
Then change the three addresses marked `ADDRESS` in `render.yaml` (or in each service's
**Environment** tab) to the real ones, and redeploy.

## 3. If the API fails to start: check the database role

The API runs the migrations when it starts. Migration 0032 (row-level security, Week 11)
creates a role, `clinic_app`, and needs the database user to be allowed to create roles.
If the API log shows `permission denied to create role`, check the user's rights from the
Codespace (the **External Database URL** from `afripeak-db` > Connect, read into a
variable as shown in section 4):

```bash
docker compose exec db psql "$RENDER_DB_URL" -c "SELECT rolname, rolcreaterole, rolsuper FROM pg_roles WHERE rolname = current_user;"
```

(On the first deploy, 1 November 2026, migrations 0001 to 0034 ran on Render without this
problem.)

`rolcreaterole` must be `t`. If it is `f`, stop and tell the team: the fix is a database
host that allows it, not removing the row-level security.

## 4. Create the first clinic and its admin

There is no shell on free services, so run the admin tool from the Codespace against the
Render database. The External Database URL contains the database password: never paste
it into a command line, a chat or a file. Read it into a variable without showing it
(paste, then Enter):

```bash
read -rs RENDER_DB_URL
```

Then create the clinic (your own clinic name, admin name and email). It asks for the
admin's password twice, hidden; at least 10 characters:

```bash
docker compose run --rm --no-deps -e DATABASE_URL="$RENDER_DB_URL" -e ENVIRONMENT=production api python -m app.cli create-clinic --clinic-name "AfriPeak Demo Clinic" --admin-name "Demo Admin" --admin-email "you@example.com"
```

```bash
unset RENDER_DB_URL
```

The same variable works for the role check in section 3: `psql "$RENDER_DB_URL" ...`.

The admin's first
sign-in at `https://afripeak-web.onrender.com/login` sets up an authenticator app (keep the
10 backup codes). The admin then adds staff on the **Staff** screen, branches and consent
wording on **Settings**.

## 5. Check it works

- `https://afripeak-api.onrender.com/health` answers `{"status":"ok"}`.
- `https://afripeak-api.onrender.com/health/ready` answers OK (database and Redis reachable).
- The landing page opens, and its **Staff sign in** link leads to the clinic app's sign-in page
  (set by `APP_URL` on `afripeak-landing`).
- The admin signs in, sees the Dashboard, and the Reminders console opens.

## Secrets

- `SECRET_KEY` is generated by Render and never leaves it. Changing it signs everybody out.
- `DATA_ENCRYPTION_KEYS` is generated by Render too. It encrypts the authenticator-app
  secrets in the database. **Never just replace it**: everyone's app would stop working. To
  change it, put the new key first and the old one after it (`new,old`); remove the old one
  only after every admin and billing person has signed in once since.
- Nothing secret is in `render.yaml` or the repository. Paystack test keys, when wanted, go
  in the API's **Environment** tab, never in a file.
